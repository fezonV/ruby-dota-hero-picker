# Инструкции для работы с проектом

## Назначение и текущий объём

Aegis Draft — Rails-приложение, которое в будущем будет помогать составлять драфты в Dota 2. Текущая итерация реализует регистрацию, вход и выход, защищённые страницы и базовый интерфейс. Каталога героев, логики драфта, рекомендаций и статистики матчей пока нет. Не описывай и не представляй их как существующие функции.

Подробное пользовательское объяснение текущей реализации находится в [`docs/guide-for-defense.md`](docs/guide-for-defense.md). Выбранное направление интерфейса и поведение фона описаны в [`DESIGN.md`](DESIGN.md); продуктовый контекст также есть в [`PRODUCT.md`](PRODUCT.md).

## Технологии и структура

- Ruby 4.0.7 и Rails 8.1.4.
- PostgreSQL; схема Active Record — в `db/schema.rb`, изменения схемы добавляй отдельными миграциями в `db/migrate/`.
- Серверная часть следует Rails MVC: маршруты в `config/routes.rb`, контроллеры в `app/controllers/`, модели в `app/models/`, ERB-представления в `app/views/`.
- JavaScript использует Importmap, Turbo и Stimulus. Контроллеры Stimulus находятся в `app/javascript/controllers/`.
- CSS приложения — `app/assets/stylesheets/application.css`; публичные изображения и общий renderer символьного Aegis — в `public/brand/`.
- Тесты используют Minitest и находятся в `test/`.

Следуй Rails-соглашениям об именах и размещении файлов. Для HTTP-логики используй контроллеры, для правил и проверок данных — модели, для HTML — представления и partials. Не добавляй отдельную архитектурную прослойку без практической необходимости.

## Аккаунты и безопасность

- Аутентификация реализована через `User#has_secure_password` и bcrypt. Никогда не сохраняй и не журналируй пароль в открытом виде.
- Разрешённые поля входных параметров должны задаваться явно через strong parameters. Не принимай произвольные параметры пользователя.
- Сохраняй нормализацию email, проверки модели и уникальный индекс базы согласованными. Проверка модели даёт понятную ошибку, ограничение базы защищает данные при конкурентных запросах.
- Для защищённых действий используй общий `current_user` и проверку авторизации до выполнения действия. Не полагайся только на скрытие ссылки в интерфейсе.
- После успешного входа сбрасывай старую сессию перед установкой ID пользователя. При выходе очищай сессию.
- При изменении форм с паролями сохраняй их очистку перед Turbo-кэшированием и не возвращай пароль в HTML после ошибки.
- Не отключай Rails CSRF-защиту и не помещай секреты в исходный код. Используй настроенные credentials или переменные окружения.

## Интерфейс и JavaScript

- Сохраняй существующую визуальную систему: тёмный фон, голубой акцент, Manrope, общие компоненты и адаптивность. Перед визуальными изменениями сверяйся с `DESIGN.md`.
- Сохраняй доступность: подписи полей, понятные состояния ошибок, видимый фокус, текстовые подписи для интерактивных элементов и поддержку `prefers-reduced-motion`.
- Фоновый Aegis декоративен и не должен блокировать формы или навигацию. Сохраняй корректную работу на сенсорных устройствах и при отключённой анимации.
- Для новых Stimulus-контроллеров корректно освобождай обработчики, observer'ы и анимационные кадры в `disconnect()`, чтобы переходы Turbo не оставляли дублирующиеся эффекты.
- Не копируй renderer Aegis в новые места: используй общий модуль `public/brand/aegis-ascii.js`, если задача действительно касается этого эффекта.

## Тесты и проверки

Поддерживай проверки рядом с изменяемым поведением. Для правил пользователя используй `test/models/`, для HTTP-сценариев — `test/controllers/`, для полного пути пользователя — `test/integration/`.

Полезные команды, перечисленные в README:

```sh
bin/rails test
bin/rails zeitwerk:check
bundle exec rubocop --cache false
bundle exec brakeman --quiet --no-pager
```

При изменениях базы проверяй миграции и обновлённую схему. В итоговом сообщении точно указывай, какие проверки были запущены и каков результат; не заявляй об успешной проверке, если она не запускалась.

## Документация и точность

Если меняются маршруты, пользовательские сценарии, схема данных, безопасность или визуальное поведение, обнови соответствующие документы, включая `docs/guide-for-defense.md`, если изменения влияют на объяснение текущей реализации. Чётко отделяй работающие функции от планов и макетов в `design/`.

# Aegis Draft: простое объяснение проекта для защиты

Этот документ объясняет текущую итерацию проекта так, чтобы её можно было рассказать без знания Ruby. Для сравнения используются знакомые идеи из Go: HTTP-маршруты, обработчики, структуры, проверки данных и HTML-шаблоны.

Для защиты последней доработки редактора есть [отдельный пошаговый гайд](draft-defense-guide.md): готовый рассказ, демонстрация, разбор Ruby-кода, пример расчёта 13 баллов и ответы на вопросы.

## 1. Что уже сделано

Aegis Draft — учебный помощник для драфта в Dota 2. В этой итерации работает полный путь от аккаунта до сохранённого состава:

- создание аккаунта по email и паролю;
- вход и выход;
- закрытая главная страница, куда попадает только вошедший пользователь;
- проверка и приведение email к единому виду;
- безопасное хранение пароля;
- страницы на русском языке с адаптивным оформлением;
- декоративный фон с символами Aegis, который реагирует на движение мыши;
- тесты для модели пользователя и основных сценариев входа;
- собственные драфты, каталог с поиском и две команды по пять героев;
- рекомендации с объяснениями, добавление и удаление с немедленным сохранением;
- HTTP integration-тест полного пути и браузерные тесты Capybara/Selenium.

На главной после входа есть кнопка «Мои драфты». Пользователь создаёт драфт,
выбирает союзников и противников, получает рекомендации и может повторно
открыть сохранённый состав после нового входа. Это учебная эвристика по
характеристикам героев (раздел 15), а не прогноз победы. Статистика матчей,
баны и очередность ходов не подключены. UI Kit остаётся демонстрацией элементов.

## 2. Как устроено Rails-приложение

Упрощённо запрос проходит так:

```text
Браузер → маршрут → контроллер → модель/база данных → HTML-страница → браузер
```

Например, при отправке формы входа:

1. Браузер отправляет email и пароль на адрес `/session`.
2. Маршрут направляет запрос в `SessionsController#create`.
3. Контроллер проверяет данные и ищет пользователя через модель `User`.
4. При верном пароле контроллер записывает ID пользователя в сессию.
5. Браузер получает перенаправление на главную страницу.

В Go эту же схему часто пишут более явно: регистрируют `http.HandleFunc`, внутри handler разбирают форму, вызывают функцию доступа к базе и выполняют `http.Redirect` или рендерят шаблон. В Rails эти части разложены по файлам и связываются соглашениями об именах.

| В Rails | Похожая роль в Go | Где смотреть в проекте |
|---|---|---|
| `config/routes.rb` | регистрация URL и обработчиков | `config/routes.rb` |
| Контроллер | HTTP handler: читает запрос и выбирает ответ | `app/controllers/` |
| Модель Active Record | структура данных плюс методы/проверки и работа с БД | `app/models/user.rb` |
| View (`.html.erb`) | HTML-шаблон, куда подставляются значения | `app/views/` |
| Миграция | изменение схемы БД, похожее на SQL migration | `db/migrate/` |
| Stimulus controller | небольшой обработчик событий в браузере | `app/javascript/controllers/` |

Условный пример маршрута и handler в Go:

```go
http.HandleFunc("/session", createSessionHandler)

func createSessionHandler(w http.ResponseWriter, r *http.Request) {
    // прочитать форму, проверить пользователя, сохранить сессию
}
```

В этом проекте назначение маршрута записано декларативно в `config/routes.rb`, а обработка — в `app/controllers/sessions_controller.rb`.

## 3. Какие страницы и адреса есть

Маршруты описаны в [`config/routes.rb`](../config/routes.rb):

| Адрес | Назначение |
|---|---|
| `/` | главная: для гостя перенаправляет на вход, для вошедшего показывает страницу проекта |
| `/registration/new` | форма регистрации |
| `/registration` | создание аккаунта после отправки формы |
| `/registration/created` | сообщение об успешной регистрации |
| `/session/new` | форма входа |
| `GET /session` | страница аккаунта для вошедшего пользователя |
| `POST /session` | проверка входа |
| `DELETE /session` | выход из аккаунта |
| `/ui-kit` | защищённая демонстрация компонентов интерфейса |
| `GET /drafts` | список собственных драфтов, новые сверху |
| `GET /drafts/new`, `POST /drafts` | форма и создание драфта |
| `GET /drafts/:id` | редактор сохранённого драфта |
| `POST /drafts/:draft_id/draft_picks` | добавление героя |
| `DELETE /drafts/:draft_id/draft_picks/:id` | удаление героя |
| `/up` | техническая проверка, что приложение запустилось |

`resource :session` в Rails — короткая запись для набора маршрутов одного текущего сеанса пользователя. Это похоже на то, как в Go можно вручную привязать несколько методов и путей к соответствующим handler-функциям.

## 4. Регистрация: от формы до записи в базе

Форма находится в [`app/views/registrations/new.html.erb`](../app/views/registrations/new.html.erb). Она отправляет email, пароль и повтор пароля. Контроллер [`RegistrationsController`](../app/controllers/registrations_controller.rb) принимает только эти поля:

```ruby
params.require(:user).permit(:email, :password, :password_confirmation)
```

Это список разрешённых полей. Он не даёт случайно принять от браузера, например, поле `admin: true`. В Go похожее ограничение можно сделать отдельной структурой входных данных и явно декодировать JSON/форму только в неё.

Контроллер создаёт объект `User` и просит его сохранить:

```ruby
@user = User.new(registration_params)
if @user.save
  redirect_to registration_created_path
else
  render :new, status: :unprocessable_entity
end
```

По-русски: «собери пользователя; если он прошёл проверки и записался — покажи страницу успеха; иначе заново покажи форму с ошибками».

Проверки находятся в [`app/models/user.rb`](../app/models/user.rb):

- email должен быть заполнен;
- email должен иметь простой формат `имя@домен`;
- email должен быть уникальным;
- если задан пароль, нужно заполнить подтверждение.

Перед проверками email приводится к единому виду: удаляются пробелы по краям и буквы становятся строчными. Поэтому ` PLAYER@Example.COM ` и `player@example.com` считаются одним адресом. В таблице базы также есть уникальный индекс для email — это дополнительная защита на уровне PostgreSQL.

Аналогия в Go: перед вставкой записи обработчик нормализовал бы адрес, вызвал функцию валидации, а затем репозиторий выполнил бы `INSERT`. В Rails Active Record объединяет объект пользователя, проверки и сохранение.

## 5. Как хранится пароль

В таблице `users` нет поля с исходным паролем. Есть `password_digest` — результат безопасного хеширования. За это отвечает `has_secure_password` из Rails и библиотека `bcrypt`.

При регистрации Rails получает пароль, вычисляет для него bcrypt-хеш и сохраняет хеш. При входе введённый пароль проверяется против хеша. Исходный пароль не восстанавливается и не нужен для сравнения.

В Go идея была бы похожа на вызов `bcrypt.GenerateFromPassword` при регистрации и `bcrypt.CompareHashAndPassword` при входе. В данном проекте эту рутинную работу выполняет Rails.

## 6. Вход и выход

Логика входа находится в [`app/controllers/sessions_controller.rb`](../app/controllers/sessions_controller.rb).

При попытке войти приложение:

1. убирает пробелы вокруг email и переводит адрес в нижний регистр;
2. проверяет, что адрес похож на email;
3. ищет пользователя с таким адресом;
4. проверяет пароль методом `authenticate`;
5. если пароль верный — очищает прежнюю сессию и записывает в новую `user_id`;
6. перенаправляет пользователя на `/`.

Если адрес или пароль неверны, страница входа показывается снова с сообщением. Значение email сохраняется в поле для удобства, пароль обратно в форму не вставляется.

Сессия — это способ помнить пользователя между запросами. В неё записывается
`user_id`; Rails передаёт данные сессии между запросами через защищённый
cookie. `reset_session` перед входом очищает прежнюю сессию.

Выход выполняет `DELETE /session`: приложение сбрасывает сессию и перенаправляет на форму входа. Это похоже на очистку данных авторизации в Go middleware/хранилище сессий.

## 7. Как закрыта главная и страница аккаунта

Метод `current_user` в [`app/controllers/application_controller.rb`](../app/controllers/application_controller.rb) достаёт пользователя по ID из сессии. Он общий для всех контроллеров, как общий helper или middleware в Go.

`HomeController` перенаправляет гостя на страницу входа. Для аккаунта и UI Kit
используется `before_action :require_authentication`: перед показом Rails
вызывает проверку и отправляет гостя войти. Поэтому прямое открытие защищённого
URL не обходит проверку. Все действия драфтов используют ту же проверку входа.
Драфт ищется через `current_user.drafts.find(...)`, а выбор — через
`@draft.draft_picks.find(...)`. Чужой и отсутствующий ресурс дают 404.

На защите можно объяснить это как middleware:

```go
func requireLogin(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        // если сессии нет — перенаправить на вход
        // иначе вызвать next.ServeHTTP(w, r)
    })
}
```

## 8. Интерфейс и фон с Aegis

Страницы используют общий каркас из [`app/views/layouts/application.html.erb`](../app/views/layouts/application.html.erb): заголовок с логотипом, навигация, содержимое страницы и подвал. В зависимости от того, вошёл пользователь или нет, в шапке показаны разные ссылки.

Общие цвета, формы и мобильные правила находятся в [`app/assets/stylesheets/application.css`](../app/assets/stylesheets/application.css). Дизайн тёмный, с голубым акцентом; на небольшом экране отступы и размеры формы меняются.

Фон — это `<canvas>`, на котором рисуются символы. Код в [`public/brand/aegis-ascii.js`](../public/brand/aegis-ascii.js) загружает изображение Aegis, уменьшает его до сетки ячеек, смотрит на яркость каждой ячейки и выбирает подходящий символ. Получается приглушённый текстовый силуэт.

При движении мыши символы рядом с траекторией временно заменяются другими. Сам знак не перемещается и не размывается. Это декоративный эффект: он не участвует в регистрации, входе или расчётах. Сенсорное движение не обрабатывается; системная настройка `prefers-reduced-motion` отключает анимацию. Когда страница скрыта или фон больше не виден, лишняя отрисовка приостанавливается.

[`glyph_mark_controller.js`](../app/javascript/controllers/glyph_mark_controller.js) подключает renderer к странице и освобождает обработчики при уходе со страницы. В браузере этот небольшой controller играет роль обработчика событий, похожего на JS-код рядом с HTML-шаблоном в Go-приложении.

## 9. Показать/скрыть пароль и Turbo

Кнопка с глазом меняет тип поля между `password` (символы скрыты) и `text` (значение видно). Код находится в `togglePassword` того же Stimulus controller.

Turbo ускоряет переходы между страницами, частично сохраняя HTML в браузере. Перед тем как форма попадёт в такой кэш, обработчик `beforeCache` очищает поля пароля, возвращает их в скрытое состояние и сбрасывает подпись кнопки. Это предотвращает сохранение введённого секрета в снимке страницы.

В Go-серверной части аналога нет: это поведение целиком выполняется на стороне браузера, поэтому сравнивать его лучше с JavaScript-обработчиком формы.

## 10. Структура базы данных

Текущая схема находится в [`db/schema.rb`](../db/schema.rb). Её создали две
миграции: [`create_users`](../db/migrate/20260926112000_create_users.rb) и
[`create_draft_models`](../db/migrate/20261023110000_create_draft_models.rb).

| Таблица | Что хранит |
|---|---|
| `users` | уникальный email, bcrypt-хеш `password_digest`, даты создания и обновления |
| `heroes` | имя, роль, четыре целочисленные учебные оценки 0–3 и даты |
| `drafts` | `user_id` владельца, название до 100 символов и даты |
| `draft_picks` | `draft_id`, `hero_id`, сторону `ally`/`enemy`, место 1–5 и даты |

Внешние ключи связывают драфт с пользователем, а выбор — с драфтом и героем.
Уникальные индексы и `CHECK`-ограничения защищают правила данных даже при
обходе проверок модели; подробности приведены в разделе 15.

Миграция — версионируемое изменение базы. Вместо ручного редактирования таблиц
разработчик добавляет миграцию, а Rails применяет её и обновляет схему. В
Go-проекте это соответствовало бы SQL-миграции, например `CREATE TABLE users ...`.

## 12. Короткий рассказ на защите

> В этой итерации пользователь регистрируется, отдельно входит и создаёт свой драфт. Через каталог он заполняет две команды и получает рекомендации с баллами и объяснениями. Каждый выбор сохраняется в PostgreSQL, поэтому после нового входа состав остаётся. Контроллеры проверяют владельца, модели — правила данных, а база — ограничения. Ruby-код следует обычной схеме Rails: маршрут, контроллер, модель и ERB-шаблон. JavaScript только фильтрует каталог и рисует декоративный фон. Подбор учебный: характеристики заданы вручную, статистики матчей нет.

## 13. Возможные вопросы и короткие ответы

**Почему пароль не хранится обычным текстом?**

Потому что при утечке базы исходные пароли нельзя будет прочитать напрямую. Хранится bcrypt-хеш, который подходит для проверки введённого пароля.

**Почему email приводится к нижнему регистру?**

Чтобы один и тот же адрес не создавал разные аккаунты из-за заглавных букв или пробелов по краям.

**Зачем проверять уникальность и в модели, и в базе?**

Проверка модели даёт человеку понятное сообщение. Уникальный индекс в PostgreSQL защищает данные на уровне базы, даже если два запроса придут почти одновременно.

**Что произойдёт, если гость откроет главную вручную?**

Контроллер проверит текущую сессию и перенаправит его на форму входа.

**На каком языке написана логика?**

Серверная часть написана на Ruby с Rails. Для отображения используются HTML-шаблоны ERB; интерактивный фон и кнопка показа пароля работают на JavaScript.

**Готов ли советник по героям?**

Да, как учебный сценарий: в редакторе можно выбрать героев, получить объяснимый совет и сохранить состав. Это простая эвристика, не анализ реальной статистики. UI Kit отдельно показывает демонстрационные компоненты.

## 14. UI Kit для демонстрации интерфейса

После входа на главной есть кнопка «Открыть UI Kit» (`/ui-kit`). Это защищённая
галерея компонентов на основе выбранного дизайна: цвета, Manrope, кнопки,
поля и ошибки, карточки героев, пять слотов команды, пустое состояние и
образец объяснения рекомендации. Общие компоненты используют CSS приложения,
а карточки и слоты оформлены Rails-partials в `app/views/shared/ui/`.

Поиск по имени или роли и выбор карточки работают в браузере через Stimulus.
Это только демонстрация UI: выбор не сохраняется, команда не изменяется,
рекомендация не вычисляется. Карточки заданы прямо в представлении, а не
загружены из `Hero`. На защите нельзя представлять эти образцы
как готовую бизнес-логику драфта. Тест `ui_kit_controller_test.rb` проверяет
защиту страницы и наличие компонентов; сквозной тест аккаунта дополнительно
проверяет сохранение авторизации при повторном запросе и закрытие доступа после выхода.

## 15. Модели драфта и учебный подбор

Редактор использует эти модели для создания и повторного открытия составов.
UI Kit по-прежнему является отдельной демонстрацией и не подключён к данным драфта.

- `Hero` — имя, роль и четыре учебных характеристики от 0 до 3:
  поддержка, контроль, урон и стойкость. `db/seeds.rb` загружает 12 героев;
  значения выставлены вручную для демонстрации, не взяты из статистики матчей.
- `Draft` принадлежит `User`, имеет название и набор выборов `DraftPick`.
  Контроллеры загружают только собственные записи через `current_user.drafts`.
  Поэтому подстановка чужого ID не даёт доступа.
- `DraftPick` связывает героя с драфтом, командой (`ally`/`enemy`) и местом 1–5.

Внешние ключи исключают ссылки на отсутствующие записи. Уникальный индекс
`draft_id, hero_id` запрещает повтор героя в обеих командах. Второй уникальный
индекс `draft_id, team, position` запрещает занятое место. Проверка диапазона
1–5 вместе с уникальностью места ограничивает каждую команду пятью героями,
в том числе при конкурентных запросах. Характеристики и команды также имеют
CHECK-ограничения. Модельные валидации дают ошибки до записи в базу.

`Draft#recommendations` исключает уже выбранных героев и возвращает героя,
баллы и список объяснений. Для союзников заданы пороги покрытия:
поддержка 3, контроль 4, урон 5, стойкость 3. Дефицит — положительная разница
между порогом и суммой характеристики союзников. Герой получает по 2 балла
за каждую единицу покрытого дефицита (не больше собственной характеристики).
Если суммарная стойкость противника не меньше 4, добавляется характеристика
урона кандидата. Результат сортируется по баллам, затем имени и ID. Для полной
союзной команды возвращается пустой список. Это простая объяснимая эвристика,
а не прогноз победы или полноценный анализ контрпиков.

Три файла `hero_test.rb`, `draft_test.rb`, `draft_pick_test.rb` проверяют
корректность данных, владение через связь пользователя, подбор и его объяснения,
исключение занятых героев, заполненную команду, удаление драфта и ограничения БД
при обходе валидаций модели. `test/integration/draft_flow_test.rb` проверяет
полный путь, владение, позиции, 422, удаление и сохранность.
`test/system/drafts_test.rb` использует реальные клики и поиск в Chrome/Chromium,
проверяет перезагрузку, новый вход и отсутствие горизонтального переполнения
на компьютере и телефоне.

## 16. Как редактор сохраняет выбор — простыми словами

В проекте не добавлено сервисов или отдельных архитектурных слоёв.
`DraftsController` показывает список, форму создания и редактор.
`DraftPicksController` добавляет и удаляет героев. ERB отвечает за HTML,
`hero_search_controller.js` — только за поиск по имени или роли.

В каталоге, заполненных слотах и рекомендациях герои узнаются по официальным
портретам Valve. Изображения хранятся локально в `public/heroes/`, поэтому для
показа не нужен запрос к внешнему API или CDN. `HeroesHelper` сопоставляет имена
героев с файлами, а общий partial `shared/ui/hero_portrait` выводит картинку.
Исходные PNG имеют размер 256×144; на странице они уменьшены до 80×45 px
(64×36 px на телефоне и в слотах), без растягивания и обрезки. Текстовые имена,
роли и доступные названия кнопок сохранены. Источники — в `public/heroes/README.md`.

При добавлении обычная форма отправляет `hero_id` и `team`. Strong parameters
разрешают только эти поля, поэтому присланные владельцы, чужие драфты и позиции
игнорируются. Создание самого драфта принимает только `title`; владельца задаёт
`current_user.drafts.build(...)`.

`Draft#add_pick` делает три шага внутри `with_lock`:

1. Блокирует строку драфта в PostgreSQL на время операции. Второй запрос к тому
   же драфту ждёт завершения первого.
2. Получает занятые позиции выбранной стороны и находит первую свободную из 1–5.
3. Проверяет и сохраняет выбор. Если места нет, добавляет понятную ошибку.

Это похоже на критическую секцию с mutex в Go, но блокировку обеспечивает база,
поэтому она действует и между разными процессами Rails. Удаление использует ту
же блокировку. Удалённое место снова доступно для выбора.

Повтор героя, неверная сторона, отсутствующий герой и полная команда дают
ответ 422 с объяснением без изменения базы. Успех даёт 303: браузер открывает
редактор заново, сервер пересчитывает рекомендации и показывает «Состав сохранён».
После добавления страница возвращается к каталогу героев, чтобы прокрутка не
сбрасывалась к заголовку редактора.
Выбранная сторона каталога передаётся отдельно как `catalog_team`; кнопка
рекомендации всегда отправляет `team=ally`. Этот параметр интерфейса не меняет
правила модели. При пяти союзниках показано «Команда собрана».

## 17. Короткая демонстрация преподавателю

Перед показом: `bin/rails db:prepare`, `bin/rails db:seed`, `bin/rails server`.

1. Зарегистрироваться и показать, что вход выполняется отдельно.
2. Открыть «Мои драфты», создать «Состав для защиты».
3. Выбрать Axe и Juggernaut в свою команду, найти поддержку через поиск по роли.
4. Переключиться на противников, выбрать Tidehunter и Centaur Warrunner.
5. Показать настоящий балл и причины рекомендации. Нажать «Добавить в мою
   команду» и показать, что союзник добавлен, хотя каталог смотрит на противников.
6. Довести число союзников до пяти. Показать «Команда собрана», удалить одного,
   увидеть рекомендации и снова заполнить освободившееся место.
7. Открыть список, выйти, войти и повторно открыть тот же состав.
8. Объяснить границы: 12 учебных героев, оценки заданы вручную; нет статистики,
   вероятностей победы, банов и очередности ходов.
